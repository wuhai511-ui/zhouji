01

背景与目标

预付费行业的资金安全问题已成监管焦点，产品能力必须先行，避免监管落地时失去承接位置。

监管驱动

教培 / 健身 / 美业 / 亲子 / 餐饮预付卡资金安全问题频发，各地陆续出台存管、限额、冷静期要求；最高法已确立 7 天冷静期、霸王条款无效。

风险窗口

一旦地市教育 / 商务部门强推预付费监管，若无现成产品承接，将重演「数电发票」式的被动局面。

既有积累

此前已做过一版设计（B 端后台 + C 端小程序），因争议仲裁过于复杂而中止；业务需求分析与店务通银行存管方案已成型。

三层目标

层级目标
短期拿出"能承接监管要求"的最小可用产品（MVP），避免监管落地时被动
中期形成「收单 + 资金存管 + 清分」标准能力，切入教培 / 本地生活头部客户
长期抽象为通用型资金存管能力，上承各行业应用封装，形成可复制的商业模式

拉卡拉不做仲裁；V1 规则 =「N 天自动默认确认 + 规则偏商家 + 复用支付投诉流程」
3
账户底座优先级
V1 支付账户验证 → V2 银行内部户 → 数币智能合约列为远期观察
4
外部借力

5
首发场景
教培（重庆）+ 本地生活（美容 / 健身 / 按摩）两者都要
6
交付载体
V1 复用小冲 / 店务通后台做规则配置；同步规划独立 C 端小程序 / 钱包
7
商业模式口径
对外按「监管费 ~1% + 收单 0.3% + 沉淀分润」表述，与内部一致
8
项目立项
以资金存管产品为主体发起立项

核心设计原则

支付与分账解耦
付完即结束，不让资金长期挂账、不把分账越做越复杂。
规则偏商家
产品卖给商家，默认向商家倾斜，同时做好消费者投诉应对。
不碰裁判权
无平台 / 监管身份，不承担仲裁；争议走既有外部流程。
底层通用、上层封装
底层抽象通用能力，各行业做应用层封装与包装。
银行优先、支付账户过渡
银行账户有沉淀与公信力但周期长；先用支付账户跑通逻辑。
自动化为先
规则可配置、到期自动扣划 / 自动确认，减少人工介入。
03

目标场景与规则模型

以三类扣款场景覆盖教培与本地生活的主要形态，规则引擎按"触发方式 + 金额模型"统一抽象。

场景类型扣款特征典型行业规则模型
包月 / 包期每月固定金额，按期自动扣健身、包月美容、物业费分期时间触发 + 固定金额
一课一销按次核销，扣款时点动态教培、亲子、单次服务核销事件触发 + 金额固定
按项目 / 行为消费内容不同、金额不同美业（泡脚 / 高级项目）、SPA消费事件触发 + 动态金额

规则要素（配置维度）

清分基数 · 清分比例/金额 · 清分时点（实时 / D+n / 月结） · 触发方式（时间 / 核销 / 确认） · 退款与扣回规则 · 争议默认处理（N 天自动确认）

清分规则（承接既有需求分析）

按服务进度清分
按月 / 按课 / 按次比例清分。
按消费次数清分
次数越多单次越优惠（阶梯）。
按消费者评价清分
满意全额清分，有问题扣一定比例作保证金。

能力架构：双模式 · 双轨并行

录音明确「两种模式都得具备」——模式 A 预付费托管（自建）与模式 B 先享后付（借力支付宝安心付）。架构升级为双轨并行，共用内核、分离账户执行层。

应用层
教培模板健身模板美业模板C 端小程序
交付 / 包装层
用户侧交付商户侧交付对商户屏蔽底层差异开箱即用
服务层
合同方案商户入驻消费者开户/签约规则配置核销对账
模式编排层
模式 A 预付费托管（资金划转/存管）⇄模式 B 先享后付（授信/代扣）
内核层
规则引擎定时任务核销引擎记账 / 映射扣款 / 清分指令退款联动
能力接入层
自建：支付账户(V1) / 银行内部户(V2) / 数币账户(V3 远期)外部：支付宝安心付（服务商模式）其他信用付 / 合作银行产品
收单 / 入金
拉卡拉全支付（码牌 / POS / 线上 / 聚合）

相比初版结构新增两层：模式编排层（决定走哪条轨）与 能力接入层（把安心付等外部能力与自建账户底座并列接入）。

核心模块要点

模块说明
规则引擎支持包月 / 一课一销 / 按项目的定时化与事件化规则配置；可先基于小冲 / 店务通后台实现
账户映射消费者预存余额 ↔ 商户应收之间的映射关联，向商户清晰展示应收
核销引擎一课一销的核销动作（上传资料、刷脸 / 打卡、签字等凭证）
清分指令生成清分指令下发至账户体系执行（支付账户 / 银行）
退款联动退款路径设计与清账（商家先退 → 账户侧清掉 → 回退）
C 端查询余额、已付 / 未付、服务记录、账单（小程序 / 钱包）

安心付整合方案（模式 B：先享后付）

自建体系只覆盖"资金已划转的托管模式"；录音明确两种模式都得具备。安心付代表「钱不划转、授信 / 代扣」的先享后付模式——路径是 成为安心付服务商：支付宝输出能力，我们做前端交付 + 中间运营包装。

模式 A · 预付费托管

自建
  • 资金状态：已划转、托管冻结
  • 商家应收：形成应收账款、可周转
  • C 端体验：需预付全款、有压力
  • 合规背书：银行托管、监管认可
  • 适配：教培 / 健身等大额长期

模式 B · 先享后付

借力支付宝安心付
  • 资金状态：未划转、授信 / 代扣
  • 商家应收：未形成应收、周转弱
  • C 端体验：先享后付、无压力
  • 合规背书：依赖支付宝信用体系
  • 适配：小额高频、锁客 / 提转化
架构层安心付的整合方式
能力接入层作为"信用付 / 先享后付"通道，与自建账户底座并列（钱不划转，不占用存管账户）
模式编排层按场景路由：需资金托管 / 合规背书 → 模式 A；要"无预付压力 / 锁客" → 模式 B
内核层规则引擎输出"何时扣、扣多少"，经 API 驱动安心付扣款；对账口径归一
交付 / 包装层复用同一套用户侧 / 商户侧前端，对商户屏蔽底层差异，做开箱即用
商业以服务商身份获取服务分润

依赖与待确认：安心付是否对机构开放、接口与政策清单、分润与费率结构、合规与责任边界。落地节奏：V1 自建存管先跑通；安心付并行调研，可行则在 P2/P3 作为第二通道接入。

05

账户底座演进（模式 A）

先用支付账户把规则与全流程跑通 → 再叠加银行内部户；数币智能合约列为远期观察。

V1 · 验证与过渡

支付账户

可快速跑通逻辑与规则、可做 demo / 试点。

注意：升单体验问题、公信力弱、无沉淀

V2 · 主战场

银行内部户

银行背书与公信力、资金沉淀收益、符合监管预期。

注意：信用卡充值不支持（仅借记卡）、退款联动复杂、周期长

V3 · 观察 / 试点

数币账户 + 智能合约

包月自动扣款天然匹配。

注意：一课一销需叠加资料 + 确认多因子后复杂；能力尚不具备

本节为模式 A（预付费托管）的账户底座；模式 B（先享后付）的载体是支付宝安心付等外部能力。苏州、重庆的数币智能合约预付费卡试点持续跟进。

争议与风控规则（V1 基线）

历史版本因"仲裁过于复杂"而中止。V1 采取极简规则，把裁判权交还外部流程。

环节规则
消费者确认服务完成后消费者确认；N 天（7/15 天）未确认自动默认确认
清分前置商户提交服务完成证明（拍照 / 刷脸打卡 / 签字等），平台做基础校验
争议立场规则偏商家，同时准备消费者投诉应对
仲裁归属拉卡拉不做裁判；争议走支付投诉逻辑 / 消协流程
事后处理消费者可对单笔提出退款诉求，按约定规则处理
