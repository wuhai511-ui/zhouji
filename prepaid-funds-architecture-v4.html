Prepaid Funds Control · Architecture Review

预付资金受控与履约清分平台
总架构汇报 V4

从“做一个存管账户产品”升级为：监管规则驱动 + 履约证据驱动 + 多资金底座适配的技术基础设施。重点修正两点：补齐养老强监管场景，以及让合同/退款逻辑服从全国司法硬基线，不再由商户规则任意定义。

02 / 08
National Baseline

先把“真实合同规则”放到司法与监管硬基线下面

平台规则优先级应变成：司法/监管硬约束 ＞ 行业/地方正式规则 ＞ 合同约定 ＞ 商户配置。
01 · 冷静期
7日无理由退款适用于司法解释覆盖的生活消费预付式消费，法定例外除外。
02 · 退款责任
先判断“谁的原因”非消费者原因：已履约部分原则按折扣价/优惠比例；消费者原因：原则按打折前价格。
03 · 本金/赠送
必须拆账实付本金、赠送金、赠送项目需要独立记录，退款按司法规则与合同共同计算。
04 · 证据责任
消费记录要可举证次数、金额、余额、履约凭证、触达记录都必须留痕，不能只存一个“余额”。

合同仍需真实调研，但它解决的是“参数”

退款折算、手续费/违约金、有效期/延期、赠送金、停课/转让/转店/冻结等仍需拿真实合同校准；但合同不能越过司法和监管硬线。

产品数据模型必须同步改变

新增 refund_reason、original_price、discount_price、principal_balance、bonus_balance、evidence_bundle、rule_source 等核心字段，才能重算与举证。

全国司法基线：最高人民法院法释〔2025〕4号，自 2025-05-01 施行。

05 / 08
Contract × Evidence × Pricing

业务内核真正的难点：不是“事件从哪来”，而是“能不能信、怎么算、能不能退”

合同规则中心

真实合同用于校准有效期、暂停/转让/转店、违约金、项目原价/优惠价、赠送权益。但司法/监管硬基线优先。

合同版本固化 规则来源留痕

履约证据中心

扫码、人脸、闸机、SaaS课消、消费者确认、设备记录都不是天然可信。需要做可信等级 + 反套现风控。

集中核销 非营业时段 批量异常

计价与退款重算

支持固定/按次/按周期/按项目/套餐分摊/动态补差，并能根据退款原因切换原价、优惠价、赠送比例等计算路径。

本金/赠送拆分 可追溯重算
不再成立的旧表述：“退款计价由商户配置即可”。正确口径是：商户可配置，但必须受司法/监管规则约束；系统先识别退款责任与适用规则，再调用合同参数。

07 / 08
Dual Money Lines

双线资金模型：支付结算与存管释放必须分开

线① 标准收单结算线

1
消费者支付 / 微信支付宝银行卡等
2
拉卡拉按支付业务规则完成收单与清算
3
资金按支付结算路径进入约定商户结算账户
4
不能把备付金变成长周期预付存管池

线② 存管 / 受控资金释放线

1
资金进入银行专户 / 信托 / 公证 / 数币钱包等合规底座
2
履约证据 + 监管/合同规则 → 形成标准资金指令
3
银行/受托方/钱包执行 Release / Freeze / Refund
4
释放后形成已履约商户应收，再做总部/门店/渠道清分
边界：“存管释放 ≠ 分账”。先判断商户已履约应得多少，再处理总部、门店、教练/技师、渠道、服务商之间的清分。拉卡拉输出规则与指令，不以自身过渡户长期归集后再向下游分配。
08 / 08
Management Conclusion

汇报结论：产品要从“账户方案”转成“规则 + 证据 + 资金执行适配”

产品定位

不做资金池，不做服务质量裁判。
做监管规则、合同/权益、履约证据、计价、确认/退款、资金指令、清分对账的技术基础设施。

场景切入

教培/体育 P0、健身 P0+、养老 P1、美业/按摩 P2。
物业作为多子余额/持续履约能力验证；小额按摩作为模式B验证。

MVP前置 Gate

银行是否支持 Release / Freeze / Refund；账户法律属性；二清边界；地方监管认可；真实合同样本；SaaS履约数据可信度。

可复制壁垒

规则引擎 + 履约证据中心 + 多底座适配 + 连锁清分。换银行、换信托、换数币或外部信用渠道，上层业务内核不重做。

最终不是“卖一套银行存管账户”，而是形成一套多监管模式下的履约资金控制平台。

资料口径：截至 2026-09-21；正式规则、指导文件、司法解释、平台实践均分层展示，实际商用前仍需银行/监管/法务逐项确认。
