预付资金受控与履约清分平台
总架构汇报 V4

从“做一个存管账户产品”升级为：监管规则驱动 + 履约证据驱动 + 多资金底座适配的技术基础设施。重点修正两点：补齐养老强监管场景，以及让合同/退款逻辑服从全国司法硬基线，不再由商户规则任意定义。

01 / 14
National Baseline

先把“真实合同规则”放到司法与监管硬基线下面

平台规则优先级应变成：司法/监管硬约束 ＞ 行业/地方正式规则 ＞ 合同约定 ＞ 商户配置。
01 · 冷静期
7日无理由退款适用于司法解释覆盖的生活消费预付式消费，法定例外除外。
02 · 退款责任
先判断“谁的原因”非消费者原因：已履约部分原则按折扣价/优惠比例；消费者原因：原则按打折前价格。
03 · 本金/赠送
必须拆账实付本金、赠送金、赠送项目需要独立记录，退款按司法规则与合同共同计算。
04 · 证据责任
消费记录要可举证次数、金额、余额、履约凭证、触达记录都必须留痕，不能只存一个“余额”。

合同仍需真实调研，但它解决的是“参数”

退款折算、手续费/违约金、有效期/延期、赠送金、停课/转让/转店/冻结等仍需拿真实合同校准；但合同不能越过司法和监管硬线。

产品数据模型必须同步改变

新增 refund_reason、original_price、discount_price、principal_balance、bonus_balance、evidence_bundle、rule_source 等核心字段，才能重算与举证。

全国司法基线：最高人民法院法释〔2025〕4号，自 2025-05-01 施行。

重点区域政策汇总｜点击卡片查看各地明细

同一“预付”问题，现实中存在全额托管、比例存管、消费者钱包、服务信托、公证提存、数币智能合约等多条技术路线。

产品结论：监管规则必须是运行时决策层，而不是写死在某一账户产品里。输入：地区 × 行业 × 客群 × 商户类型 × 金额 × 期限/次数 × 底座/保障方式；输出：是否可售、监管比例、账户要求、确认/退款、释放条件。

01

核心结论：三条红线不可越

项目在P0层面成立，但合规路径唯一。"预付资金受控释放＋按履约进度清分"与当前监管方向高度一致，落地必须走银行专用存款账户存管＋持牌机构按指令清分。

红线 01
支付机构备付金账户不得用于长期存管。备付金属短期中转、100%集中存管人民银行，预收资金须进银行专户或信托专户。
红线 02
资金不得先归集到平台账户再分配，平台不得自行清算或截留商户资金。划转由银行或持牌机构执行，不做二清。
硬约束 03
各行业/地区的存管比例与收费上限是硬指标。教培"3月/60课时/5000元"、北京存管≥20%、上海40%专户、养老保证金≥10%。

典型场景：先看业务，再抽象规则

平台不从账户能力出发，而从真实业务场景出发。六个典型场景覆盖预付式消费的主要形态，每个场景的问题清单和规则结论是规则引擎设计的直接输入。

S1游泳课时包模式A · 按次履约 + 逐次释放
消费者购买20节游泳课共4,000元，一次性支付全款进入受控状态。每完成一节课，由SaaS/教练系统产生履约记录，消费者确认后释放本次课时资金，未消费部分随时可退。
关键设计点

履约凭证：扫码/签到/SaaS核销/教练确认（多方式可配）
自动确认：商户可配置N天（平台设上限，如N≤7天）
退款计价：按套餐单价或重算规则，签约时固化
争议处理：窗口内冻结当前课时金额，不冻结整个合同

标准流程
1签约购课 → 全额支付
2资金进入受控余额
3预约上课 → 履约/核销生成消费记录
4消费者确认/自动确认 → 本次课时金额释放
5剩余资金继续受控 → 未消费部分支持退款
S2健身年卡模式A · 时间周期履约 + 周期释放
消费者购买12个月健身年卡共3,600元，一次付款进入受控状态。按自然月/固定周期释放，支持跨门店履约（总部统一合同），暂停会籍可顺延服务期限。
关键设计点

释放方式：自然月、固定周期、按次（商户可配置）
暂停处理：会籍暂停+释放暂停+服务期顺延（按合同规则）
跨门店：总部统一会员体系，按实际履约门店清分
停业/闭店：强监管项目停止后续释放进退款流程

标准流程
1购买年卡 → 全额支付
2资金受控 → 周期履约
3消费者确认/自动确认
4按实际履约门店清分 → 剩余资金继续受控
S3美业项目包模式A · 项目履约 + 动态计价
消费者支付5,000元购买组合美容套餐（护理、美甲、美容项目、需多次完成的疗程），各项目结算金额不同。支持跨门店消费、临时升级、按次或全部完成后释放。
关键设计点

项目计价：商户提前配置每个项目的结算价格
退款规则：签约时配置退款计价规则，系统自动计算
跨门店：总部统一管理合同和会员，按实际履约门店清分
升级补差：优先使用套餐余额，不足部分补差并与原合同关联

标准流程
1购买组合套餐 → 全额支付
2资金受控 → 门店履约 → 计算结算金额
3消费者确认 → 释放项目资金
4总部、门店等进一步清分 → 剩余资金继续受控
S4物业预缴模式A · 持续履约 + 多资金子余额
消费者选择季度/半年/年度预缴物业费（含物业费、停车费、增值服务），各费用形成独立资金子项，每个子余额拥有独立的履约规则、释放规则和争议状态。
关键设计点

资金子余额：物业费/停车费/增值服务各自独立，独立履约/释放/退款规则
投诉分流：如停车位争议只冻结停车费子余额，基础物业费继续正常处理
房屋出售/退租：支持剩余资金退款或权益转移（根据合同规则）
月末自动确认：展示本期服务及金额，无异议自动确认

标准流程
1选择预缴套餐 → 签署合同 → 支付
2周期触发履约 → 消费者查看本期服务
3无异议自动确认 → 对应子余额释放
4剩余余额继续受控
S5小额按摩先享后付模式B · 先履约 + 后扣款
消费者首次进入门店签署先享后付授权，完成一笔198元按摩服务，不需要事先充值。服务完成后系统产生应付账单并向消费者扣款，扣款失败自动重试并通知补缴。
关键设计点

授权模式：单次授权/长期授权/额度型授权
账户能力：支付宝安心付、银行信用付、其他授权代扣产品
争议分流：未扣款→暂停扣款进争议；已扣款→不进回滚，进售后退款流程
扣款失败：自动重试 + 通知补缴，超限进欠款/风险处置流程

标准流程
1消费者授权
2商户服务 → 履约完成 → 生成应付账单
3判断是否需要二次确认 → 扣款
4扣款成功 → 商户结算/清分
S6养老机构模式A · 强监管多资金Bucket
养老必须补入总架构，不能用一个"预付余额"概括：服务费、押金、会员费具有不同期限、账户和支取规则。涉及高息返利、预售床位、承诺保本的机构应作为高风险准入/拒绝合作场景。
关键设计点

服务费预收≤12个月、押金≤月床位费12倍
押金/会员费进入银行第三方存管专户
未入住及时全额退款；已入住扣除消费金额原路退
风险保证金≥近三年会员费总额10%且≥账户余额20%

标准流程
1选择入住套餐 → 签署合同
2支付押金/服务费 → 进入银行存管专户
3按月释放服务费 → 退住时结算剩余
4风险保证金留存 → 异常监测预警

Contract × Evidence × Pricing

业务内核真正的难点：不是“事件从哪来”，而是“能不能信、怎么算、能不能退”

合同规则中心

真实合同用于校准有效期、暂停/转让/转店、违约金、项目原价/优惠价、赠送权益。但司法/监管硬基线优先。

合同版本固化 规则来源留痕

履约证据中心

扫码、人脸、闸机、SaaS课消、消费者确认、设备记录都不是天然可信。需要做可信等级 + 反套现风控。

集中核销 非营业时段 批量异常

计价与退款重算

支持固定/按次/按周期/按项目/套餐分摊/动态补差，并能根据退款原因切换原价、优惠价、赠送比例等计算路径。

本金/赠送拆分 可追溯重算
不再成立的旧表述：“退款计价由商户配置即可”。正确口径是：商户可配置，但必须受司法/监管规则约束；系统先识别退款责任与适用规则，再调用合同参数。

总架构：规则横向治理，六层纵向落地

七大核心模型

所有行业最终统一到这七个模型，每个模型是一个可配置的技术模块。场景决定规则，规则驱动履约，履约触发资金动作。

合同模型
套餐/项目/价格/期限/退款/暂停/跨店/自动确认等规则，签约时固化
履约模型
统一产生 Fulfillment Event（扫码/签到/API/SaaS/时间周期触发）
计价模型
计算本次履约对应金额（固定/按次/按周期/按项目/动态/套餐分摊/补差等）
确认模型
主动确认、自动确认、提出争议的处理逻辑
争议/退款模型
待释放冻结、已释放售后、剩余资金退款、退款计价
资金执行模型
标准指令 Release/Debit/Freeze/Refund，上层不直接接触资金
清分模型
总部、门店、教练/技师、渠道、服务商之间的资金分配

两种资金模式并行

模式A · 预付资金受控释放

自建（V1支付账户→V2银行内部户→数币远期）
  • 资金状态：已划转、托管冻结、按履约进度释放
  • 商家应收：形成应收账款、可周转
  • C端体验：需预付全款、有压力
  • 合规背书：银行托管、监管认可
  • 主要覆盖：游泳课时、健身年卡、美业套餐、物业预缴

模式B · 信用授权按次扣款

借力支付宝安心付/银行信用付
  • 资金状态：未划转、授信/代扣、服务后扣款
  • 商家应收：未形成应收、周转弱
  • C端体验：先享后付、无压力
  • 合规背书：依赖支付宝/银行信用体系
  • 主要覆盖：小额按摩、小额即时服务、高频低客单
双模式并行：需资金托管/合规背书→模式A；要"无预付压力/锁客"→模式B。模式编排层按场景路由，对商户屏蔽底层差异。

双线资金模型：支付结算与存管释放必须分开

线① 标准收单结算线

1
消费者支付 / 微信支付宝银行卡等
2
拉卡拉按支付业务规则完成收单与清算
3
资金按支付结算路径进入约定商户结算账户
4
不能把备付金变成长周期预付存管池

线② 存管 / 受控资金释放线

1
资金进入银行专户 / 信托 / 公证 / 数币钱包等合规底座
2
履约证据 + 监管/合同规则 → 形成标准资金指令
3
银行/受托方/钱包执行 Release / Freeze / Refund
4
释放后形成已履约商户应收，再做总部/门店/渠道清分
边界：“存管释放 ≠ 分账”。先判断商户已履约应得多少，再处理总部、门店、教练/技师、渠道、服务商之间的清分。拉卡拉输出规则与指令，不以自身过渡户长期归集后再向下游分配。

资金行为典型场景触发器资金动作主要风险

风险与行动

四条核心风险

教培机构付费意愿不足
如果机构没有付费意愿，产品将是纯成本中心
访谈5-10家目标教培机构，确认合规意愿和预算 → 置信度中
银行开放度不确定
银行是否愿意为拉卡拉开放专用存款账户体系的对接能力未经验证
与2-3家银行（上海/北京/深圳分行）沟通合作模式 → 置信度中
健身SaaS对接未打通
没有SaaS对接则入场数据获取困难，清分触发无依据
与三体云动/青橙科技BD接触，探明合作模式 → 置信度中
信托异地落地可行性低
服务信托在太原尚未落地，仅在上海/济南/苏州等试点
咨询信托公司太原业务可行性，结论后直接回填 → 置信度低

六项立即行动

01补齐监管细则：山西/深圳/江苏监管细则（定点联系当地主管部门/律师协会）
02验证付费意愿：访谈5-10家目标教培机构，确认合规意愿和预算
03银行对接：与2-3家银行沟通专用存款账户体系对接（开户/冻结/解冻/退款/监管报送）
04SaaS对接：与三体云动/青橙科技BD接触，探明健身SaaS合作模式
05法务确认：咨询法务+信托公司，明确服务信托对拉卡拉的商业模式影响
06跑通PoC：完成阶段0——1-2个典型场景全链路内部演示

汇报结论：产品要从“账户方案”转成“规则 + 证据 + 资金执行适配”

产品定位

不做资金池，不做服务质量裁判。
做监管规则、合同/权益、履约证据、计价、确认/退款、资金指令、清分对账的技术基础设施。

场景切入

教培/体育 P0、健身 P0+、养老 P1、美业/按摩 P2。
物业作为多子余额/持续履约能力验证；小额按摩作为模式B验证。

MVP前置 Gate

银行是否支持 Release / Freeze / Refund；账户法律属性；二清边界；地方监管认可；真实合同样本；SaaS履约数据可信度。

可复制壁垒

规则引擎 + 履约证据中心 + 多底座适配 + 连锁清分。换银行、换信托、换数币或外部信用渠道，上层业务内核不重做。

最终不是“卖一套银行存管账户”，而是形成一套多监管模式下的履约资金控制平台。
